# Проверки ExecRepoBench

Дата: 2026-11-03. Все перечисленные запуски выполнялись локально,
не через SSH и не на mounted server. Никакие файлы под `X:` не изменены.

- Закреплённый JSONL: SHA256, схема всех 1164 задач, шесть категорий,
  50 репозиториев; historical ответы/метрики очищаются whitelist-загрузчиком.
  Все 9592 записи ZIP прошли проверку безопасных путей.
- 27 stdlib unit/launcher-тестов прошли: данные, ID/хеши, traversal/links,
  повреждения/дубликаты JSONL, resume, exact whitespace, FIM/budget/close,
  отсутствие model imports при оценке, ES и знаменатели, полный gold gate,
  namespace/scripts, одинаковые параметры launcher, пробелы и exit codes.
- Windows PowerShell и Bash в WSL Ubuntu реально запускались. Оба `--help`
  совпадают; capture interpreter с пробелами получает точные аргументы и
  возвращает 37; отсутствующий `--python` возвращает 2.
  Отдельно проверен настоящий Windows native shim со stderr и exit=37.
  Реальный Windows reader lock воспроизводит PermissionError; повторная
  атомарная запись переживает его. После исправления pilot gold снова 12/12,
  все 12 отдельных result.json в точности совпадают с основным JSONL.
- Синтетический Docker-check подтвердил чтение изменённого файла из `/repo`,
  независимость двух параллельных задач, pass/test_fail/timeout/oom/infra,
  nonroot, отсутствие socket и удаление контейнеров. Timeout включал потомка.
- Рабочим Dockerfile собраны три пилотных образа. Gold через Windows launcher:
  12/12, 100%; empty через WSL Linux launcher: 3/12, 25%; infrastructure=0.
  Это только пилот и характеристика его тестов, не полный результат модели.
- Настоящий AutoTokenizer (Transformers 5.19.0, tokenizers 0.23.2), revision
  `b2cff646eb4bb1d68355c01b18ae02e7cf42d120`: проверены все 1164 prompts,
  1175–7168 input tokens, окно 8192 и резерв 1024 соблюдены. Native stop IDs
  совпадают с официальным примером. Независимый tokenizer.json/Jinja-check
  также прошёл все 1164. Весов, Torch, CUDA и vLLM в CPU-проверке не было.

Все 50 образов собраны с успешным финальным pip check и проверкой импортов.
Для двух native Windows build-клиентов наблюдалось зависание после сообщения
export DONE; повторный вызов того же Python-контроллера в локальной WSL завершил
сборку успешно. Docker Desktop image store общий для Windows и WSL. Это
наблюдаемое ограничение native build CLI в текущем окружении; stdin отключён
у всех неинтерактивных Docker-команд. Подготовка данных через standalone CLI
также реально проверена: source-dir, jsonl-only, 1164 чистых экспортированных задач.

Полные первичные oracle/empty прогоны завершены для всех 1164 уникальных ID.
Для каждого из 2328 результатов отдельный `tasks/<id>/result.json` в точности
совпадает с каноническим JSONL; пропусков и дубликатов нет. Использованы те же
50 готовых image IDs, исходный runtime SHA256
`ea58a419fe00c686b425b3e755e19fa674158829ed32a7bc5803faa5ed34fce2`,
по шесть workers на каждый из перекрывавшихся запусков, 2 CPU / 4 GiB / 256 PID /
240 секунд на контейнер. Oracle-контроллер запускался в Windows, empty — в локальной
WSL; Docker Desktop daemon общий. Это локальные измерения, не серверный запуск.

Oracle: **1089/1164 (93,56%)**, 75 test_fail, ноль timeout/OOM/infrastructure_error.
Полностью проходят 46 из 50 проектов. Неуспешные задачи: html-to-json — 13,
lxml_html_clean — 29, python-rasterstats — 17, truecase — 16. Диагностика показывает
расхождения HTML-дерева/экранирования, предупреждения affine, превращённые тестами
в ошибки, и отсутствие NLTK punkt в truecase. Это отказы test runner в данной
среде, а не доказательство дефекта эталонов. Зависимости/ресурсы этих четырёх
окружений требуют отдельного исследования; source/tests/выборка ради score не менялись.

Первичный empty: 285 pass, 867 test_fail, 7 timeout, 1 OOM, 4 infrastructure_error.
Четыре инфраструктурных пробела python-pinyin отдельно повторены через
`retry_controls.py` с одним worker, исходными образами/кодом/лимитами. Первичные
попытки сохраняются; test_fail/timeout/OOM не заменяются. ID 859/861/869 стали
test_fail; ID 872 повторно дал infrastructure_error: runner exit=1, container
exit=120, хотя в stdout видны 10 неуспешных тестов. Протокол консервативно
оставляет этот исход неизвестным. Итоговый empty: **285 подтверждённых pass**,
870 test_fail, 7 timeout, 1 OOM, 1 infrastructure_error. Полная доля не определена;
нижняя граница — 285/1164 (24,48%), при успешном неизвестном ID верхняя —
286/1164 (24,57%). Ни один empty pass не исключён. Финальная сводка и
первичные/повторные статусы сохраняются в [control_report](control_report/report.html),
JSON-доказательствах и CSV всех ID. До полного gold 1164/1164 модельный полный
score запрещён контроллером; текущий oracle этого условия не выполняет.

Все 285 успешных empty относятся к ID, для которых oracle также прошёл тесты.
Это наблюдаемая нечувствительность тестов к удалению вставки в данных условиях;
такие задачи сохраняются в исходном знаменателе. ES: oracle 100,00%, empty
1,8900%, знаменатель обоих — 1164. [HTML](control_report/report.html), Markdown,
CSV и JSON сверены по ID/статусам/суммам категорий и проектов. Финальный HTML
проверен в изолированном Chromium на 1440×1000 и 390×900: поиск, focus, прокрутка
таблиц, раскрытие диагностики, отсутствие page errors/HTTP-запросов и чтение
без JavaScript. Desktop/mobile screenshots просмотрены; внешнего overflow нет.

Сохранён отдельный [каталог меток](control_report/task_labels.json) и CSV всех
1164 ID: `test_fail` — ровно 75 oracle test_fail, `empty_green` — ровно 285 empty
pass. Списки `id_sets` и флаги CSV независимо сверены с измеренными результатами;
пересечений нет, без обеих групп остаётся 804 задачи. ID 872 сохраняет неизвестный
empty-исход и не получает этих меток. `task_labels.py score` проверен на полном
oracle (1089/1164), исключении test_fail (1089/1089), исключении обеих (804/804)
и выборе empty_green (285/285). Это аналитические подмножества; исходная оценка
и полный gold gate сохраняются. Проверены неверные ID/хеши/дубли, пересечения
меток, неполные входы, infrastructure_error, защита исходного summary от записи;
measurement runtime SHA256 остался прежним.

Общее локальное окружение по разрешению пользователя приведено к рабочей паре
Transformers 4.45.2 / huggingface-hub 0.36.2 / tokenizers 0.20.1; импорт
AutoTokenizer проверен. Для точной 5.19.0 использовано отдельное
`.venv-tokenizer`, `pip check` там проходит. Общее окружение имеет прежние
конфликты сторонних приложений и не объявляется полностью согласованным.

Не подтверждены: установка/драйвер/GPU/engine на Linux-сервере, загрузка модели,
реальная генерация, persistent resume после падения настоящего vLLM. Для них
есть server-only команды в README; они выполняются пользователем.
